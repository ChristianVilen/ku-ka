# Selected Area Screen Capture (app name Ku-Ka (kuvakaappaus))

## Overview

A lightweight macOS app to replace the default `Shift+Command+4` selected area screenshot functionality. The app will:

- Capture a user-selected area of the screen.
- Capture a window with `Shift+Command+4`, then `Space` and a click.
- Capture the full screen instantly with `Shift+Command+3` (captures the screen where the cursor is, with flash animation).
- Multi-monitor support — dims all screens, captures from the screen where the cursor is.
- Save the screenshot to `~/Screenshots/`.
- Copy the screenshot to the clipboard.
- Floating thumbnail preview after capture — click to annotate with freehand drawing.
- Delete screenshots from thumbnail or editor — removes file and clears clipboard.
- Keep Awake — prevent the Mac from idle-sleeping from the menu bar, for a preset time (30m/1h/2h/4h) or until turned off, with an optional "keep display awake" preference.
- Window tiling — `Ctrl+Option+Left/Right/Return/C` snaps the active window to the left half, right half, full screen, or center of its display (maximize toggles back to the previous frame; center keeps the window's size and does nothing when it's already maximize-sized). Pressing Left/Right again on an already-snapped window sends it to the same half of the next screen in that direction (wrapping — with two monitors, either direction reaches the other one). Stage Manager-aware, with a Settings switch to turn the hotkeys off.
- Clipboard history — `Shift+Command+C` opens a glass panel listing recorded clipboard items, newest first; typing filters, arrow keys select, Enter pastes into whatever app had focus. For rich text (RTF/HTML), Enter opens a chooser: paste with formatting or without, with "without" pre-selected. Records plain text, rich text, and images, including Ku-Ka's own screenshots — deleting a screenshot removes its history entry too. In-memory only, capped at 100 items and ~100 MB of image bytes; concealed/transient/auto-generated pasteboard content (password managers) is never recorded. A Settings switch stops polling, clears the history, and releases the hotkey.
- Meeting notes. **Start Recording Meeting** in the menu records the microphone ("Me") and the sound the Mac plays ("Them") through one ScreenCaptureKit stream. A floating panel shows the state and the recorded time, with Pause, Resume, and Stop, and opens into a live transcript draft from Apple's `SpeechTranscriber`. The draft stays in memory and never goes to disk. Pause keeps no audio until Resume, and each resume leaves 3 s of silence in both files. After Stop, Ku-Ka transcribes both tracks on the Mac with WhisperKit (model `large-v3-v20240930_turbo`), or with Apple's `SpeechTranscriber` when Whisper cannot start, tells apart the voices on the microphone track with SpeakerKit ("Room 1", "Room 2", and so on, when it finds two or more), merges the tracks, and asks an AI command-line tool for a summary. Automatic tries `agy`, then `claude`; explicit Antigravity or Claude Code uses only the selected tool. Each meeting gets a folder `<meetings folder>/<yyyy-MM-dd_HH-mm>/` with `transcript.md` and `summary.md`. The audio goes to the Trash once the transcript exists. The transcript text leaves the Mac as the CLI's prompt, with the known words that occur in it and the whole optional meeting-context file. Known words: a Markdown list (`knownWordsFile`, by default `known-words.md` in the meetings folder) of wrong forms and right forms. Ku-Ka replaces the forms marked ✓ in `transcript.md`, gives the CLI the relevant words, and gets back suspect words in the same reply. It asks about at most 5 of them per meeting in a review window, which the notification or **Check Words** in the menu opens, inserts each answer as a new line in the list, and **Update Notes** makes the transcript and the summary again with the answers.

## Architecture

Calendar reminders use `CalendarOccurrence`, `CalendarReminderController`, `CalendarReminderStore`, `EventKitCalendarSource`, `CalendarReminderNotifications`, and `CalendarReminderDriver`. `AppDelegate.calendarReminders` is the optional app-owned controller behind the Settings window's Calendar reminders switch. Enable through `setEnabled(_:) async`, never a defaults-only write. Only `AppDelegate` constructs it, and XCTest and `--uitesting` never construct `AppDelegate`. `SystemNotifier` is the sole notification delegate. Forward recorder changes through the existing Meeting Notes callback. See `docs/calendar-recording-reminders.md` for exact interfaces and identity limits. Tests must inject calendar fields, notification-center calls, and driver signals. Never use a real EventKit store, real notification delivery, capture, or model downloads in these tests.

The reminder controller owns one typed offer and one validating or associated recording link. Only the notification adapter cleans up pending or failed native adds. `CalendarEventFields` requires the provider source. Use `"synthetic"` only in tests.

Optional `meeting.json` display-title metadata does not change dated folder names or meeting stages. `MeetingRecorder.displayTitle` fixes the title for its session. `MeetingNotesController` shows a bounded title in the existing status line and retains the full title in its tooltip and accessibility label.

It maps a host time to recorded time (the paused spans left out, what the timer shows) and to a file position (recorded time plus `resumeGap`, 3 s, for each earlier resume), and maps a file position back to recorded time. `fileIntervalInOneRun(from:to:)` maps a host interval to one `FileInterval` only when both ends are in the same recording run, so an interval that crosses a pause gives nil. `keptFileIntervals(from:to:)` clips a closed host interval to the kept runs and gives one `FileInterval` for each piece. A point inside a run gives a zero-length interval, a point at a Pause gives none, and a point at a Resume maps after the resume gap. Only the clock reads its stored pause and resume host times; other code gets derived values (`pauses`, file positions, file intervals) and never rebuilds the runs. `cut(start:frameCount:sampleRate:)` returns a `BufferCut`: which frames of one buffer to keep, the file position of each kept piece, and whether the buffer ends in a pause. Only the clock can make a `BufferCut`. A change only adds a boundary after the last one, so the mapping of any earlier time never changes. `RecordedTime.format(_:)` writes a recorded time for the menu, the panel, and its rows: "4:05", or "1:02:09" from an hour |
| `LiveTranscript` / `LiveUpdate` / `LiveResult` | Pure, in memory only. `LiveUpdate` is what the live engine reports: `started`, `unavailable(reason)`, `result(LiveResult)`, or `failed(reason)`. A `LiveResult` is one analyzer result in file positions, with its text as phrases that each have their own times. `LiveTranscript` keeps the final phrases and at most one volatile tail per track, and a `Status` (`preparing`, `live`, `unavailable`, `failed`). A tail holds all phrases of the newest volatile result, and the next volatile result replaces them as a whole. `preview(on:)` builds the drawer's `LivePreview` in recorded time: the final rows from `Transcript.merge` with no join and no room labels (the order and echo rule of `transcript.md`, one row per phrase), each phrase of an unsettled tail by its start, one row per pause, and `behind` when the newest result was 4 s or more old when it arrived. A tail that a later `finalizedThrough` passes becomes final. `settleTails()` at Pause shows each tail as final, and a later result for the same audio still replaces it |
| `AppleLiveTranscriber` / `LiveTranscribing` | The live engine behind the `LiveTranscribing` seam. `updates(locale:audio:)` returns an `AsyncStream<LiveUpdate>` at once. It reports `unavailable` when `SpeechTranscriberAdapter.needsDownload(for:)` throws or says that the model is not installed, and it never downloads or reserves a model. Otherwise each track gets its own `SpeechTranscriber(locale:preset: .timeIndexedProgressiveTranscription)` and `SpeechAnalyzer`, which read that track's `WrittenAudio` with each buffer at its file position (`WrittenAudio.startTime`). `LiveResult.init(track:range:finalizationTime:text:)` splits each result into phrases: after `.`, `?`, or `!`, and at a pause of `LiveResult.phrasePause` (0.7 s) or more between two words. A phrase runs from the audio time of its first word to that of its last. Text without word times is one phrase over the result's range. When the reader of the stream goes away, a cancel handler calls `cancelAndFinishNow()` on each analyzer |
| `MeetingControlsPanel` / `MeetingTranscriptDrawer` / `MeetingPanelPlacement` / `TranscriptFollow` | `MeetingControlsPanel` is a `FloatingPanel` subclass and a pure view, like `ClipboardPanel`. The panel keeps the shape it drew last, and a drag, a resize, a screen change, and Restore Default Position lay out that shape, so they never build the transcript rows again. The drawer owns its views, the rows, `TranscriptFollow`, and the scroll position. It never activates Ku-Ka and does not make itself key when it appears (`becomesKeyOnlyIfNeeded`), so a click on Pause or Stop leaves the keyboard with the meeting app. `hidesOnDeactivate` is false, and it joins all Spaces. Show Meeting Controls makes it key, so Tab reaches its buttons. Esc closes the drawer, and End returns to live. ## Requirements

### Functional Requirements

1. **Selected Area Capture** — Triggered by `Shift+Command+4`, user selects rectangular area with visual feedback (crosshair, dimensions).
2. **Full Screen Capture** — Triggered by `Shift+Command+3`, instantly captures the screen where the cursor is with a flash animation.
2. **Save to Screenshots Folder** — PNG saved to `~/Screenshots/` as `Screenshot_YYYY-MM-DD_at_HH-MM-SS.png`.
3. **Copy to Clipboard** — Captured image automatically copied to clipboard.
4. **User Experience** — No persistent window, menu bar agent only. Floating thumbnail preview after capture. The floating meeting controls show only while a meeting is recorded, and briefly after it ends.

### Technical Requirements

- **Language**: Swift 5, macOS 26.0+ (raised for `NSGlassEffectView`, used by the clipboard history panel)
- **Build tools**: Xcode 26+ / Swift 6.2+ compiler in Swift 5 language mode. The shortcut owners use `isolated deinit` for main-actor resource cleanup.
- **Project format**: Xcode 16 synchronized folders (object version 77) — opening the project needs Xcode 16 or later
- **Frameworks**: AppKit, Carbon.HIToolbox (global shortcut registration), CoreGraphics, ScreenCaptureKit, ServiceManagement, ApplicationServices (Accessibility API for window tiling), ImageIO (clipboard-panel thumbnails), CryptoKit (SHA-256 content hashing, via `ContentHash`), AVFAudio (meeting audio files), AVFoundation (Microphone permission), Speech (`SpeechTranscriber`: the fallback and the live transcript), OSLog (`Log`), UserNotifications
- **Packages**: The Swift package https://github.com/argmaxinc/argmax-oss-swift is the only third-party dependency, pinned to exactly 1.1.1. Only the KuKa app target links its `WhisperKit` and `SpeakerKit` products. Only `WhisperKitTranscriber.swift`, `SpeakerKitRoomLabeller.swift` (for SpeakerKit, and WhisperKit's audio loader), and their tests import them
- **Permissions**: Accessibility (window move/resize and synthetic clipboard paste), Screen Recording (ScreenCaptureKit), Microphone (Meeting Notes only). Registering shortcuts requires neither permission; using their actions can still require a grant.
- **Launch at Login**: `SMAppService.mainApp.register()` / `unregister()`
- **Build flag**: the KuKa app target sets `OTHER_SWIFT_FLAGS = "-enable-upcoming-feature IsolatedDefaultValues"`. This exists because `WindowTilingController`'s init has default argument values (`AccessibilityWindowControl()`, etc.) that construct `@MainActor` types, and under Swift 5 language mode the compiler otherwise treats those defaults as evaluated outside the actor. The flag becomes redundant once the project moves to Swift 6 language mode, where this is the default behavior.

## Implementation Notes

### Keyboard shortcuts
- All seven shortcuts use public Carbon `RegisterEventHotKey` registrations on the main actor. There is no keyboard event tap or Secure Input polling.
- Screenshot combinations use `kVK_ANSI_3/4` with `cmdKey | shiftKey`. Clipboard history uses `kVK_ANSI_C` with the same modifiers. Tiling uses `kVK_LeftArrow/RightArrow/Return/ANSI_C` with `controlKey | optionKey`.
- Carbon matches each registered combination; additional Command/Control/Option/Shift modifiers are not part of that registration. Ku-Ka no longer captures screenshot variants with extra modifiers.
- One `onAction` callback carries `HotkeyAction`. Turning a feature off unregisters its combinations so other apps can use them.
- Before registering, check enabled macOS shortcuts with `CopySymbolicHotKeys`. Do not assume a successful registration proves there is no conflict. If the lookup fails, report and retry rather than register blindly.
- Keep Shift+Command+3/4. If they conflict, the menu directs the user to Keyboard Settings > Keyboard Shortcuts > Screenshots to turn off the matching macOS bindings. Ku-Ka does not change system preferences.
- Show screenshot shortcut setup once when conflicts are first detected, after permission setup. The `didShowScreenshotShortcutSetup` setting persists across launches. Closing or choosing Later leaves the menu instructions available.
- Registration errors affect only their shortcut. A failed release stays in the registrar's pending-release state and remains visible even when that feature is disabled. `HotkeyManager` retries on its 5-second timer and menu open, preserving successful registrations. A newly enabled system conflict releases the affected registration. Wake/session activation renews registrations.
- The menu lists unavailable shortcuts and missing Accessibility permission together. It never assigns blame to an app or promises lock/unlock will fix an issue. The red dot in the icon's bottom-left corner means a shortcut or Accessibility problem; orange there means Screen Recording is missing. The recording mark (top-right) is a red dot with a white centre while recording and two white bars while paused, so it does not depend on colour alone.
- Registration success is not a check of physical delivery, window movement, capture, or synthetic paste. In particular, paste can still fail in protected fields.

### Screen Capture
- Overlay window is dismissed before capture to exclude it from the screenshot.
- 50ms delay after dismissal ensures the overlay is fully gone.
- `CGWindowListCreateImage` with `.optionOnScreenOnly` and `.bestResolution`.
- Coordinate conversion from NSView (bottom-left origin) to CGDisplay (top-left origin).

### Selection Overlay
- `OverlayWindow` at `.screenSaver` level, borderless, transparent.
- `SelectionView` draws dimmed background (30% black), clears selected rect, white border, monospaced dimensions label.
- Escape key cancels selection.
- Zero-size selections are ignored.

### Logging
- New log lines use `Log.<category>` from `KuKa/Log.swift`, not `NSLog`. `Log` writes to the unified log with the subsystem `com.kuka.screenshot` and one category for each area: `app`, `capture`, `tiling`, `hotkeys`, `permissions`, `keepAwake`, `clipboard`, `meeting`, and `teams`. It has `info`, `notice`, and `error`. Only `Log.teams` has callers so far, and the rest of the app still uses `NSLog`.
- `LogMessage` applies the privacy rule of `os.Logger`. Numbers, Booleans, and `PublicLogValue` values (such as `TeamsScanReason`) are public. Any other interpolated value is `<private>` unless the call says `privacy: .public`. Mark a value public only when it can never hold meeting content.
- `LogMessage` writes `<private>` into the text before `Log` sends it, and `Log` sends the whole text as public. So a private value stays hidden also on a Mac that shows private log data.
- In zsh, `log` is a shell builtin. Run the macOS tool as `/usr/bin/log`, for example `/usr/bin/log stream --predicate 'subsystem == "com.kuka.screenshot"'`.

### Test-Mode Guard

`main.swift` selects the host once through `AppLaunchMode`. `XCTestConfigurationFilePath` selects a passive host with no application delegate, even when `--uitesting` is also present. XCTest never constructs `AppDelegate` or its production controllers and services. Meeting tests use a temporary folder, never `~/Meetings`.

Without XCTest, `--uitesting` selects `SettingsPreviewAppDelegate`. It owns isolated `KuKa.TestHost` defaults, an inert login adapter, one Settings window, and `StatusMenu(sections: [])` with a static icon. Menu Settings and Command-comma open the same window. The preview has no runtime feature callbacks, permission handling, polling, recovery, or model work. Production uses `AppDelegate` with private Settings and no test-mode branches.

### Window tiling implementation

- All layout math works on `visibleFrame` (menu bar and Dock excluded) in NS (bottom-left) coordinates.
- Stage Manager insets on maximize: 7% of visible width on the left (`stageManagerLeftInsetFraction`), 2% of visible *height* on top, bottom, and right (`stageManagerEdgeInsetFraction`; height-based on all three so the gaps are equal in points). Applied only when Stage Manager is on **and** the screen has 2+ windows — with one window the strip hides itself. Half-screen tiling gets no inset.
- Maximize/restore toggle: restore fires when the window's current frame matches the previously *achieved* frame (not the requested one) within 2 pt (`frameMatchTolerance`). This handles apps like Terminal that snap sizes to a character grid.
- Screen hop: a Left/Right press on a window already sitting at that half's target (within the same 2 pt tolerance) moves it to the same half of the adjacent screen in that direction. Screens are ordered by horizontal center (`TilingScreenRules.adjacentScreenIndex`) and the step wraps, so with two monitors either direction reaches the other one. Judged against the ideal target, not an achieved frame — an app that snaps its size by more than 2 pt never hops and just gets the half re-applied (accepted).
- Center (`Ctrl+Option+C`): moves the window to the middle of the visible frame keeping its size. Does nothing when the window's size already matches the maximize target's size within 2 pt (position is ignored); with the Stage Manager strip taking space, "maximize size" means the inset stage target.
- Screen rules: a window "belongs" to a screen when at least 50% of its own area intersects it; Stage Manager's own windows (owner `"WindowManager"`) and zero-area windows are excluded from the count. A window is tiled against the screen it overlaps the most; ties go to the lowest index, and with no overlap the controller falls back to `NSScreen.main`, then the first screen.
- AX safety: a 0.5 s `AXUIElementSetMessagingTimeout` cap stops a hung app from stalling the main thread; attributes are checked with `AXUIElementIsAttributeSettable` before writing; position is written before and after size for reliable edge snapping; the achieved frame is re-read and returned. Ku-Ka refuses to tile its own windows (pid check). Failures are only `NSLog`ged — no user feedback.
- The `windowTilingEnabled` `UserDefaults` key defaults to on. `WindowTilingController.savedFrames` entries for closed windows are never cleaned up (accepted for v1).
- `StageManagerDetector` reads `com.apple.WindowManager` / `GloballyEnabled` fresh on every access; this works because the app is unsandboxed.

### Meeting notes implementation

- Recording meters read the same converted PCM that `AudioTrackWriter` writes. `append` returns one `WrittenAudio` with its RMS for each converted buffer it wrote. The RMS leaves out timeline-padding silence and the frames of a converter drain. A buffer inside a pause returns none, so the meters go quiet during a pause. `ScreenCaptureRecording` keeps the latest per-track measurement and monotonic receipt time in a `RecordingAudioMeter` under a short `OSAllocatedUnfairLock`. Main-actor `ActiveRecording.audioLevels()` copies this scalar state without waiting on the audio queue or holding a lock during disk I/O. Each reading expires after 0.5 seconds. The pure model maps -60...0 dB to 0...1.
- `MeetingNotesController` shows a `RecordingAudioMeterView` below the recorded time while recording or paused, with the levels from `MeetingRecorder.audioLevels()`. Its 0.1-second common-mode timer runs only while the menu is open. `MenuSection.menuDidClose()` is a protocol requirement with a no-op default, and `StatusMenu` forwards the close event. Closing the menu, stopping, interruption, shutdown, and deinit invalidate the meter timer. The view owns no recording state. Quiet audio has no warning.

- The meeting folder is the only processing state that survives a restart. Teams observations are temporary in-memory input, not another stage record. `MeetingStage` comes from the files: `summary.md` means done, `transcript.md` means the summary is next, and audio means the transcription is next. An `error.md` turns the next step into a failed step. No stage is stored anywhere. The hidden heard copy `.transcript-as-heard.md`, `review.json`, and `review-skipped.json` never change the stage.
- Every text file is written atomically (temporary file, then rename). The stage rule reads "`transcript.md` exists" as "transcription finished", so a half-written file must never exist under the real name.
- `MeetingProcessor.process` moves `audio/` to the Trash at the start of the summarize step, the first moment a transcript is known to be on disk. A failed transcription keeps the audio. So does a meeting with no speech: it writes `summary.md` first, which marks it done, so the summarize step never runs for it.
- Known words act only in the summarize step and in Update Notes. "Known words implementation" below has the rules.
- `summary.md` is the title and the notes, and nothing else. When an earlier CLI failed before one wrote the notes, the processor logs the CLI that wrote them and each failure with `NSLog`. When every CLI fails, `error.md` lists each one, as before. Update Notes writes no `error.md`: the meeting stays done, and its old `summary.md` stays.
- At launch, `resumeUnfinished()` queues every pending meeting. Failed meetings wait for **Retry Failed Meeting**, which removes `error.md` and queues them, so the processor starts again at the failed step. Update Notes from the review window is a job in the same queue, after the meetings before it, so it never runs at the same time as a summary. Quit cancels processing, a running Update Notes, and the jobs that wait, and terminates a running CLI. Nothing is marked failed, so the next launch continues. Update Notes jobs are not stored: after a quit, the user asks again.
- One writer owns a folder at a time, also across two Ku-Ka processes (a debug build next to the installed app). On disk, a live recording looks like a crashed one, so the recorder holds `MeetingFolder.lock()` while it records or is paused and the processor holds it for each run. A locked folder is skipped. The system releases the lock when the process ends, so crash recovery is unchanged. The recorder never writes after `stop()` returns.
- Threads: `MeetingAudioCapturing.start` is `@MainActor`, so `ScreenCaptureRecording.stream` is touched only there; the sample buffers run on the recording's own queue. The queue copies the `RecordingClock` once per buffer from an `OSAllocatedUnfairLock`, and only `apply(_:)` on the main actor replaces it, so the queue never waits on the main actor. The transcriber, session, and `WhisperKitLibrary` methods that do long work, `SpeakerKitRoomLabeller.roomLabels`, the `SpeakerKitLibrary` methods, `AppleLiveTranscriber`'s run, `Summarizer.summarize`, and `ProcessCommandRunner.run` are `@concurrent`, so they stay off the main actor even after a move to Swift 6 or `NonisolatedNonsendingByDefault`, where a plain nonisolated async function would run on the caller's actor.
- The capture can end before `startRecording(title:)` returns, while the recorder is still `.starting` and drops the callback. `ActiveRecording.endReason` is set on the main actor before `onInterrupted` runs. `startRecording(title:)` checks it once the handle is back and first verifies that the same session still owns the start attempt.
- Capture uses one `SCStream` with `capturesAudio`, `captureMicrophone`, and only the `.audio` and `.microphone` outputs. Measured on macOS 27: both tracks arrive without a `.screen` output, both use the host clock (the first buffers were 70 ms apart), and a CAF file that `AVAudioFile` was writing is readable after `kill -9`. The microphone format depends on the device (24 kHz for AirPods, 48 kHz for the built-in microphone), so each `AudioTrackWriter` builds its converter from each buffer's own format.
- The origin of a recording is the host time (`HostTime.now()`, `CMClockGetHostTimeClock`) that the recorder reads just before `capture.start`. Recorded time 0 and file position 0 are both at the origin. So the timer and a Pause in the first second work before any buffer arrives, and both files start with silence for the time the capture takes to start.
- Unit tests cannot show which clock the stream stamps its buffers on. On each track's first buffer, `ScreenCaptureRecording` logs the offset from the origin ("first ... buffer starts N s after the clock origin"). Only the first buffer of the recording, on either track, is checked. If its offset is below -1 s or above 60 s, the recording stops with "Ku-Ka could not match the audio clock (offset N s)." instead of padding a wrong amount of silence. The check runs before `append`, so a rejected buffer writes nothing. The other track's first buffer is not checked, because ScreenCaptureKit may send no system audio while the Mac plays nothing, so it can start much later. It is padded with silence as usual.
- Pause and Resume change only the `RecordingClock`. The `SCStream`, the writers, the files, and the folder lock stay, so Resume cannot fail, and the system microphone indicator stays on while paused. At a click, the recorder reads the host time, adds it to its clock, and hands the recording a copy in one main-actor step (`updateActive`). A buffer reaches the sample queue only after its audio was captured, so no buffer already written holds audio from after the click. The queue cuts every later buffer by the new clock. It keeps the frames before a pause, drops the frames inside it, and cuts a buffer that crosses a boundary at the nearest frame. Both tracks use one clock, so both cut at the same host time.
- At a pause, `AudioTrackWriter` drains the converter and resets it, so no frame from before the pause comes out after the resume gap. The converter holds back a few frames (6 at 48 kHz, measured, under 1 ms). `drain()` loops while `convert` returns `.haveData`, because `.endOfStream` comes only on a later call that returns no frames. The drained frames go to the file only, not to the meters or the live feed.
- Each resume adds `RecordingClock.resumeGap` (3 s) to the file position, and `AudioTimeline` writes the gap as silence in both files. The gap is longer than the 2 s join gap of `Transcript.merge`, so the final transcript never joins speech across a pause. The gap is in the files but not in the recorded time. So each time in `transcript.md` is 3 s later than the panel showed for each earlier pause. No file records the pauses, so crash recovery needs nothing new. Whether Whisper writes a silence phrase into the gap is not measured yet.
- The panel and the menu show recorded time, which stands still while paused. While paused, the menu's status line is "Paused · <time>", the record item still says **Stop Recording Meeting**, and the quit alert is the same as while recording.
- The live transcript is a draft. It lives in `ActiveMeeting.State.live`, never goes to disk, and goes away at Stop. The final pass after Stop is unchanged, and `transcript.md` still means that transcription finished.
- `AppleLiveTranscriber` runs only when `SpeechTranscriberAdapter.needsDownload(for:)` says that the model for `meetingLocale` is installed (`SpeechTranscriber.installedLocales`). It never starts a download. Do not use `AssetInventory.status(forModules:)` for this check. In the research run, it returned `supported`, not `installed`, for an installed en-US model. Only the English models come installed, so another supported language gets live text only after its model is installed, for example by an earlier Apple fallback run. Every other locale, Finnish included, gets "Live transcript is not available for <language> on this Mac.", and the details go to `NSLog`. The engine also requires that `SpeechAnalyzer.bestAvailableAudioFormat` is `AudioTrackWriter.fileFormat`, because the analyzer does not convert audio.
- The analyzers read `WrittenAudio`, the converted buffers that `AudioTrackWriter` wrote, so paused audio never reaches them. Each buffer goes in at its file position, and a jump in position at a resume or after a dropped buffer tells the analyzer that the audio has a hole. `WrittenAudio.startTime` rounds the position to the nearest frame. `CMTime(seconds:preferredTimescale:)` rounds down, which made a buffer start one frame early and overlap the one before, and Speech then ended the analysis with error 17.
- `LiveAudioFeed` keeps the newest 256 buffers (about 5 s) per track and drops the oldest, so a slow analyzer never slows the sample queue. The behind chip shows the lag instead. The lag is measured when a result arrives, so in silence the chip keeps its last value. The engine runs while the panel is hidden or the drawer is closed, so the drawer shows the whole meeting when it opens. Measured with generated speech, Apple's `localspeechrecognition` process used 1.4 to 2.2% of one core at the median.
- Stop, an interruption, and quit cancel the recorder's live task. That ends the reader of the update stream, and the cancel handler calls `cancelAndFinishNow()` on each analyzer. Cancelling the task alone does not stop Speech's input loop. A live task can already hold an update when Stop cancels it, so `applyLive` checks the folder and drops an update from an earlier meeting.
- Speech logs "Cannot use modules with unallocated locales [en_US] ... This will be an error in a future release!" Ku-Ka reserves no locale with `AssetInventory.reserve(locale:)`, neither for the live engine nor for the Apple fallback. A future macOS may need the reservation.
- Measured with `RealLiveTranscriptTests` on a generated two-track meeting of 253.7 s at real-time pace, with `.progressiveTranscription`, the first text came after 1.09 s. Final text came a median of 0.94 s (Me) and 0.85 s (Them) after its audio.
- The live view has one row per phrase and never joins rows. `transcript.md` still joins a speaker's segments under 2 s. In a room, several people share the microphone track, so a short gap on one track can be a new speaker. Apple cuts a result at a pause, not at a new voice, so one result can hold the sentences of two people. The engine splits each result after `.`, `?`, or `!` and at a pause of 0.7 s (`LiveResult.phrasePause`) or more between two words. A row shows the time of its first word. A new speaker stays in the row before when the text before has no sentence end and the pause is shorter.
- The live engine uses `.timeIndexedProgressiveTranscription`. This is a deliberate change from the decision in the research note (`docs/superpowers/research/2026-10-27-floating-meeting-panel.md`, decision 3), which chose `.progressiveTranscription`. Only the time-indexed preset gives each word its audio time (`audioTimeRange`), and the split into phrases needs it. The research run measured Apple with this preset. Measured with `RealLiveTranscriptTests` on a generated room meeting of 296.6 s at real-time pace, with three voices on the microphone track and one on the system track: the first text came after 1.09 s, and final text came a median of 0.93 s (Me) and 0.91 s (Them) after its audio. Every word time was inside its result's range. Of the 43 turns that follow another person on the microphone track, 42 started a new row.
- The echo rule applies to each final phrase. A phrase is shorter than a result, so the rule more often hides a real microphone sentence of 3 or more words when a system phrase within 1 s shares 60% of its words. In the room meeting it hid 2 sentences: "Nothing from me." before "Nothing from me either.", which is the one turn above without a row, and "I will be your backup." after "... if someone from your side is my backup."
- `MeetingRecorder` owns every fact the panel draws: the phase, the recorded time, the hidden and drawer flags, the notice, and the live preview. The panel only renders `controls` and calls the recorder, so the state has tests without AppKit, and the panel tests need no processor. `controls.preview` is nil while the transcript drawer is closed, so a 1 s tick does not rebuild the rows. `LiveTranscript` merges the final segments again only when they change. Each `ActiveMeeting` starts with the drawer closed. macOS has no supported way to keep a window out of a shared screen (`NSWindow.SharingType.none` is no longer used), so meeting text shows only after the user opens the drawer.
- The panel is a non-activating `FloatingPanel` at `.floating` level with `hidesOnDeactivate` set to false, because Ku-Ka never activates and an `NSPanel` hides when its app deactivates. AppKit keeps only titled windows on screen, so `MeetingPanelPlacement` moves the pill back onto a screen after a drag or a display change. The pill keeps its top-right corner, so it grows to the left when a state makes it wider.
- After Stop, the pill says "Recording saved" for 6 s (`MeetingRecorder.afterSixSeconds`). The delayed close captures only the folder. The `ActiveMeeting` holds the folder lock, and processing needs the lock at once, or it returns `.busy`. An interruption notice stays until the user closes it. Both notices show also when the user hid the panel. There is no "Saving" state, because `stopRecording()` closes the files in one main-actor step.
- `Settings.meetingControlsTopRight` (key `meetingControlsTopRight`, the pill's top-right corner as `[x, y]` in global NS coordinates, nil for the default) and `Settings.meetingTranscriptHeight` (key `meetingTranscriptHeight`, default 280 pt, which the panel clamps to 140 to 460 pt) hold the position and the drawer height. The panel writes them only when a user drag or resize ends, never at launch or for a move of its own, because construction must not rewrite saved preferences. Restore Default Position removes the saved corner.
- Ku-Ka has one status item. Stop is in the panel and in the menu, and both call `stopRecording()`. **Hide panel** in the drawer header keeps the recording going, and **Show Meeting Controls** in the menu brings the panel back and makes it key.
- `RealLiveTranscriptTests` runs Apple's model for `meetingLocale` on real audio at real-time pace, so it takes about as long as the audio. The model must already be installed. One test, for an unsupported locale, loads no model and runs in the default suite. The other two are skipped unless `KUKA_LIVE_AUDIO` names a folder with `me.caf` and `them.caf`. When the folder also has a `manifest.json` with the script of a generated meeting, the test checks that the final text has more than 80% of each speaker's words. In a room meeting, the manifest names the person in `speaker` and the track (`me` or `them`) in `track`. The test then also reports how many turns that follow another person on the same track start a new row, and which microphone phrases the echo rule hides:

  ```bash
  xcodebuild -project KuKa.xcodeproj -scheme KuKa test -only-testing:KuKaTests/RealLiveTranscriptTests
  ```

- `MeetingControlsPanelTests/testWritesAPictureOfEachState` writes one PNG per panel state, from `01-starting` to `11-interrupted`, in light and dark. It is skipped unless `KUKA_PANEL_SNAPSHOTS` names a folder:

- A transcript has "Me" or room labels on its microphone lines, never both. `Transcript.merge` gives a microphone segment its voice from `RoomVoices.voice(for:)` after the echo and empty-text filters, so a voice that only echoed "Them" gets no number, and the numbers run 1...N without a gap. Two more rules decide which voices count. Diarization of the whole microphone track can give the echo of "Them" a voice of its own, and short echoes (under the echo rule's 3-word limit) survive the echo rule. So a voice is an echo voice when its kept segments overlap "Them" speech for at least 70% of their time (`echoVoiceTimeShare`) and at least half of its words, by count, are in the "Them" segments near its own (`echoVoiceWordShare`). "Near" is the echo rule's time test with its 1 s slack, and words are compared as in the echo rule, with case and punctuation ignored. An echo voice's lines are dropped like echoes, and it gets no number. The word test keeps a person in the room who often talks while "Them" speaks, because an echo repeats the words of "Them" and that person does not. A voice with fewer than 5 words of kept speech does not count: its lines take the label of the counted voice whose turn is nearest (`RoomVoices.keeping(_:)`, then `voice(for:)`). With fewer than two counted voices, the microphone stays "Me". A person who says only short things while "Them" speaks, mostly with words that "Them" just said, looks like an echo voice, and those lines are dropped. `markdown` writes the room legend only when a line has a room label, and today's "Me" legend otherwise. For `.failed`, the line "There are no room labels. <reason>" sits between the byline (and any "Tried first:" list) and the legend, so the summary CLI never sees it.

- `RoomVoices.voice(for:)` gives each whole Whisper segment one voice and never splits a segment, because Ku-Ka keeps no word times. About a quarter of the Them segments (124 of 517) start in lowercase. Most are fragments without punctuation, and the filter keeps them.

### Meeting context implementation

- `Settings.meetingContextFile` reads the optional `meetingContextFile` defaults key at each use and expands a leading `~`. Unset or empty means no file. `AppDelegate` supplies this path to the summarizer through `MeetingContextFile`. No context file is selected by default.
- `MeetingContextFile` reads a regular UTF-8 file with a 16 KiB (16,384-byte) cap. Reads are bounded to the cap plus one byte, so a growing file cannot cause an unbounded read. Missing or blank content gives no context. Unreadable, invalid UTF-8, oversized, and nonregular files are logged without their contents and skipped; they never fail a meeting. Files containing NUL bytes are also logged and skipped because Foundation cannot pass NUL in the `agy` prompt argument. Oversized files are omitted whole, never truncated.
- `Summarizer` reads the path and text again for each summary call, including retry and Update Notes. `SummaryPrompt` treats the complete accepted text as background data, never instructions. The transcript takes priority, and context must not supply decisions, owners, or claims absent from it. Known-word blocks and the `ku-ka-review` output contract stay in force. The existing CLI arguments, fallback order, fixed PATH, empty working folder, and ten-minute timeout stay unchanged.
- The whole context goes to Google for `agy` or Anthropic for `claude` on every use, including both providers on fallback. This differs from `knownWordsFile`, which still sends only matching forms. Keep the README disclosure, setting/removal examples, and cap/error behavior in step with the code.

### Known words implementation

- Known words act only in the summarize step and in Update Notes, which share `MeetingProcessor.correctAndSummarize`. The transcribe step writes the merged Markdown twice: as the hidden heard copy `.transcript-as-heard.md` and as `transcript.md`. `correctAndSummarize` reads the heard copy (`MeetingFolder.heardTranscript()`), reads the list once (`knownWords()`), and writes `transcript.md` again as `Transcript.corrected(heard copy, by: list.corrector)`. So `transcript.md` is always derived and never patched: a second run gives the same file, a replacement never applies twice, and a list line removed before the next run undoes its replacement. A meeting transcribed before known words has no heard copy, so its first run saves `transcript.md` without its note as the copy. Accepted tradeoff (decided by the user, 2026-10-29): Update Notes also replaces a hand edit in `transcript.md`, because it starts from the heard copy. The README and the finished page of the review window say so, and tell the user to fix words through the list.
- Files in a meeting folder, each with one writer, and none of them changes the stage: `.transcript-as-heard.md` (the processor, in the transcribe step), `review.json` (the processor, in the summarize step, before `summary.md`, because `summary.md` marks the meeting done; a run without questions removes the file of an earlier, stopped run; Update Notes never writes it), and `review-skipped.json` (only `WordReviewController`, through `MeetingFolder.saveSkip`, after `summary.md`). So a skip needs no meeting lock. Ku-Ka keeps no other record of an answer: a right word or "correct as heard" is only its line in the known-words list.
- What goes to the CLI: `contentForSummary` of the corrected `body` (without the "Known words applied" note), and only the words of the list that occur in it (`relevant(to:)`), as `heard / heard -> Right` lines and one "Correct as heard:" line. The notes, dates, and ✓ marks of the list never leave the Mac. Before the transcript, the prompt requests one fenced `ku-ka-review` block in the same reply: a JSON array of at most 10 words that speech recognition probably got wrong. The block never reaches `summary.md`, and a missing or broken block only means that there are no suspects.
- Questions: `WordQuestions.select` keeps a suspect only when its quote is in the content that the CLI got and the list does not know its heard form in any state, and keeps at most 5. A meeting gets one round: Update Notes asks nothing new. So Ku-Ka never asks the user to confirm a provisional line that the user or another tool wrote. The same rule holds after the questions are saved: `wordReview(knownWords:)` reads the list each time, and a question whose heard form the list knows now is not open, in the meeting that answered it and in every other one. Nothing is written for it in a meeting folder, so a list line removed later opens the question again, also in the meeting that answered it; only a skip stays closed. The list did not know the word when Ku-Ka asked, so a known question means that the list learned a word of this meeting, and the finished page offers Update Notes (decided by the user, 2026-10-29). Without this rule, two meetings could each get a different confirmed right form for one heard form, and the corrector would then drop that form everywhere. Questions and skips match by the heard form's tokens (`WordQuestion.key`), so punctuation that the CLI kept around a word makes no second question.
- The ✓ rule: a ✓ or ✔ confirms the heard form written just before it (back to the nearest "(", ")", ";", or "."), or every form of its segment when nothing is written there. A form without ✓ is provisional and only goes to the CLI. The corrector replaces confirmed forms only, and never a form that two right forms confirm, a form that is the right form of another word, or a correct-as-heard word. A form may differ from its own right form only in case: the answer "ChatGPT" for "chatgpt" fixes the case, and text that already is "ChatGPT" stays as it is and gets no note.
- The list is read at each use and never cached, because the user and the user's own tools also edit it. Ku-Ka only inserts lines (`KnownWordsList.adding`). It never changes or removes a line, understood or not; only a last line without a line ending gets one. So removing the inserted lines gives the old file byte for byte. An answer that the list already has writes nothing.
- `KnownWordsFile.add` takes a `FileLock` on `~/Library/Application Support/Ku-Ka/known-words.lock`, not next to the list, reads the file again under the lock, and writes the whole file atomically to the path with symlinks resolved. The lock stops only another Ku-Ka. An edit by a text editor is lost only when it lands between the re-read and the rename. A held lock is the message "Another Ku-Ka is saving to the known-words list. Try again." in the review window. Before the write, `add` reads the new text back and refuses it (`.notReadBack`) when the list would not say the answer. That happens when the line would land in a "---" block at the top or a code block that is never closed. Without the check, the answer had no effect, and each later answer added one more "## Added by Ku-Ka" heading.
- Each answer writes one file. A right word and "correct as heard" write only the list, and Skip writes only `review-skipped.json`. When that write fails, nothing is written, the question stays open, and the page shows the error. A skip file that is not a JSON object with a `skipped` array of strings counts as no skips, and the next Skip writes a new file.
- Folder values: `MeetingFolder.url` is always the meetings folder resolved with `realpath` and the meeting's name, so a folder from the setting, from a listing, or from a notification compares equal, also when the meetings folder is a symlink or under `/var`. Before this, `all(in:)` found no meeting in a meetings folder that was itself a symlink, so launch recovery, Retry, the failed count, and Check Words saw nothing.
- Ordinary words: the answer for a `.person`, `.company`, or `.product` question always gets ✓ (decided by the user, 2026-10-29). Only `.term` and `.other` questions go through `isOrdinary`, and `WordReviewController` owns that rule. The default, `OrdinaryWords.spellChecker`, is true when `NSSpellChecker` finds every word of the lower-cased heard form in the dictionary of `meetingLocale` ("en_US", else "en"), and false without such a dictionary. Then the line is provisional, and the question page says so. Measured on en-US: "my key" and "compass" are ordinary, "convio" is not, and the lower-cased name "ida" is, which is why names skip the check.
- The review window (`WordReviewWindowController`) renders `controller.screen` and keeps only view state: the question that last filled the field, so an error keeps the typed text. It shares `OrdinaryWindowActivation` with Settings and onboarding, so `.accessory` returns only after the last ordinary window closes. Tests inject policy and activation actions. `show(_:)` calls `controller.show(_:)` and also brings an open window to the front when the page does not change, because `onChange` fires only on a change. Return saves and Esc closes through the field's delegate, because the field editor would show word completions on Esc. VoiceOver does not say which part of the quote is bold, so the field's label names the heard form.
